# 新增暂停状态：守护器检测到进行中任务的执行已暂停时自动转暂停并记录原因

## 决策内容

状态机增加"暂停"状态，挂在"进行中"之后：

```
进行中 → 暂停 → 进行中（恢复执行）/ 待办（重新排队，守护器会重新派发到新 worktree）
暂停 → 已搁置 / 已废弃
```

暂停的判定用双信号，自我报告为主、活动检测兜底：

1. **自我报告（主信号）**：守护器派发任务时在 prompt 里要求执行 agent——遇到无法继续的阻塞或需要暂停时，先自己对主 checkout 执行 `wf-status.sh T-xxxx 暂停 "<原因>"` 再停下；工作期间定期更新 worktree comment 作为心跳。原因由当事人写，最真实
2. **活动检测（兜底信号）**：守护器每趟扫描进行中任务，用任务 frontmatter 里的 worktree id 经 Orca CLI 检查，满足任一即判定暂停：
   - `orca worktree show` 查不到该 worktree → "Orca worktree 不存在（可能已被删除）"
   - `orca terminal list` 显示没有 `connected: true` 的终端 → "执行终端已全部断开，分支未合并回主分支"
   - 所有 connected 终端的 `lastOutputAt` 距现在超过阈值（`WF_DAEMON_STALL_MINUTES`，默认 30 分钟）→ "执行终端 N 分钟无输出，疑似停滞"

守护器判定暂停后：`wf-status.sh T-xxxx 暂停 <原因>`（原因进 INDEX 事件备注并自动提交），并在任务文件末尾追加"## 暂停记录"小节逐条记录时间与原因。没有 worktree 字段的任务（手工执行）不做活动检测。

## 背景与理由

1. 初版"worktree 存在 + 终端 connected"被用户否了：终端连着不代表 agent 在干活（可能早停在提示符上），要看真实的活动信号（lastOutputAt 输出时间戳）
2. 双信号而非纯检测：执行 agent 自己知道为什么停（需求不清、权限不够、测试失败……），自我报告的原因质量远高于守护器的外部猜测；活动检测只兜"agent 崩溃/被杀/卡住没来得及报告"的底
3. 停滞判定用"无输出时长"而不是"TUI 是否空闲"：输出是任何 agent（不限 TUI 形态）都有的通用信号——本 skill 是全局 skill，检测逻辑不能依赖特定 agent 的界面特征；阈值走环境变量，不写死
4. 暂停不自动恢复：暂停意味着出了需要人看一眼的状况，恢复（转进行中继续 / 转待办重新派发）由用户决定
5. 原因双写（INDEX 事件 + 任务文件暂停记录）：INDEX 是事件流，任务文件是追溯链的落点，一个月后能直接在任务文件里看到"它为什么停过"

## 影响范围

- scripts/wf-common.sh：合法状态加"暂停"
- scripts/wf-status.sh：新增流转 进行中→暂停、暂停→进行中/待办/已搁置/已废弃
- scripts/wf-daemon.sh：once 流程加暂停检测（collect_merged → check_paused → dispatch）；派发 prompt 增加自我报告与心跳要求
- docs/PRD.md、SKILL.md、assets/README.md：状态机与暂停检测说明
