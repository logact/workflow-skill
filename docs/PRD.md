## 原则
1. 每个决策都要有记录
2. 用户在流程里面最小摩擦 通过在agent对话框就可以记录这些 任务，决策，bug
3. 记录的文件必须要能够从类型划分 从状态划分 不要混乱
4. 每个任务应该要能够能够让用户验收

## 场景
1. 我：首先描绘出自己的想法，首先是纵向的点这个东西要满足什么，特点是什么，要保持什么原则，这些点可能是贯穿场景的要求或者原则
	2. 我： 描绘出具体的场景
	3. 我&agent: 我把这些原则和具体场景给AI 让它给我判断是否有冲突，让它给我一些意见，把这些想法汇总形成PRD
	4. 我： 创建agent 建模任务 规定验收的场景：必须要有人工可审核的日志 + 结果层面可验证的标准（日志证明做过，结果证明做对）
	5. agent： 建模实现 ， 我： 等待
	6. 我： 验收场景根据日志记录
	7. 我： 通过agent 记录问题（每个问题创建一个文件），agent: 分别同时验证研究这些问题
	8. 我&agent：验证过一轮后，又看这些agent 处理过的文件 可能让agent 生成任务，或者讨论改变决策，把这个点记录下次做，或者遗留这个 放进backlog，或者增加修改PRD的决策
	9. agent： agent 跑这些任务 我：等待
	10. 我：验收 回到6
	11. 我：验收不通过 → 通过agent记录为问题文件 → 回到7（循环没有死端）

## 文件分类（PRD阶段就必须定下来，否则后面一定乱）
- 类型：PRD / 决策记录 / 任务 / 问题 / backlog
- 状态：起草 / 待办 / 进行中 / 待验收 / 完成 / 已搁置 / 已废弃
- 一个问题一个文件；决策变更时记录新决策，并把旧决策标记为"已被X取代"

## 关键机制
1. 记录责任在agent：对话中识别到决策点，agent主动提议一句话记录，我只负责确认。这样同时满足原则1（每个决策有记录）和原则2（最小摩擦）
2. 验收标准：每个任务创建时都必须带验收标准（不只是第一个建模任务）；日志只是审计辅助，验收必须包含结果/行为层面的标准（能跑一遍、能看产出）
3. 并行约束：多个agent同时研究问题时，只写自己的问题文件；共享索引只能追加，避免写冲突
4. 追溯链：任务文件里注明来源问题，验收记录里注明对应任务，保证一个月后还能回答"这个改动是为了什么"
5. PRD变更复查：每次修改PRD，让agent做一次轻量冲突检查（对照原则和既有决策）
6. backlog回流：每轮验收后扫一眼backlog，决定哪些条目升级为任务，防止backlog变成坟场
7. 审批门与任务调度：任务创建后进"起草"，用户审批转"待办"才可执行；任务带优先级与前置依赖，守护调度器自动把可执行的待办任务派发到 Orca worktree，分支合并回主分支即结果层面验收通过
